# حالة التنفيذ — v0.1

التاريخ: 14 أكتوبر 2026.

هذه وثيقة التنفيذ الفعلي. وثيقة `PRODUCT-ARCHITECTURE.ar.md` تظل المعمارية المستهدفة، ولا تعني أن كل مكون فيها متاح اليوم.

## 1. شريحة أولى تعمل من البداية إلى التسليم

تم بناء رحلة واحدة حقيقية على مستوى إدارة سير العمل:

إنشاء مشروع ← تشغيل تجريبي ← مسودة متطلبات ← تعديل وحفظ ← اعتماد نسخة ← تجهيز ملفات ثابتة ← فحوص بنية ← مراجعة واعتماد ← تنزيل.

البيانات وقرارات الانتقال محفوظة على الخادم؛ ليست أزرارًا تغيّر حالة مؤقتة في المتصفح. لكن إعداد المتطلبات والخطة والملفات **محاكاة حتمية** لا تستخدم مزود نموذج. الهدف هو اختبار تجربة الموافقات والتتبع والتسليم قبل إدخال تكاليف النماذج ومخاطر تنفيذ الكود.

## 2. المنفّذ والمؤجل

| الجزء | الآن | التالي |
|---|---|---|
| واجهة عربية | Next.js + React + TypeScript + CSS؛ RTL وشاشات متجاوبة | تحسينات إضافية للإتاحة وفصل مكونات الشاشة حسب نموها |
| API | FastAPI + Pydantic، عقود مدخلات وحالات تعارض واضحة | واجهة عميل مولدة من OpenAPI |
| البيانات | SQLite، معاملات `BEGIN IMMEDIATE`، وعلاقات حذف متسلسل | PostgreSQL + SQLAlchemy + Alembic وترحيل موثق |
| المشاريع | إنشاء، قائمة، بحث وتصفية، تفاصيل، حذف بتأكيد | عضويات وصلاحيات على مستوى المشروع |
| المصادقة | **غير موجودة**؛ مساحة مشتركة واحدة | تسجيل دخول وجلسات آمنة وCSRF وفحص ملكية لكل مورد |
| التنسيق | طلب `advance` يتحكم فيه الخادم ويستدعيه المتصفح عند فتح المشروع | عامل Celery وطابور Redis وoutbox وleases |
| أحداث التشغيل | أحداث محفوظة مع استجابة كل انتقال | SSE مع الاستئناف من معرف الحدث |
| المتطلبات | آخر نص محفوظ ورقم نسخة لحالة التشغيل وربط الموافقة به | جدول نسخ مستقلة لا تُمحى وإظهار فروق النسخ |
| الوكلاء | قوالب نصية حتمية، بلا اتصال خارجي | مزود واحد وراء واجهة اختبارية مع ميزانية ورموز |
| المخرجات | قالب HTML ثابت ووثائق وتقرير، محفوظة داخل SQLite | تخزين ملفات مستقل وبصمات محتوى وروابط تنزيل قصيرة العمر |
| التنفيذ | لا shell ولا تثبيت حزم ولا تشغيل كود مولد على الخادم | Runner منفصل بعزل أقوى وسياسات موارد وشبكة |
| المعاينة | iframe لقالب موثوق فقط، sandbox وCSP | بوابة منفصلة على أصل آخر للكود المولد، بمدة صلاحية |
| التسليم | ZIP بعد موافقة بشرية | تكامل مستودع محدود الصلاحيات، ثم staging باعتماد مستقل |

### لماذا SQLite الآن؟

لتوفير تشغيل محلي بحد أدنى من الإعداد، وإثبات المسار كاملًا قبل إضافة عدة خدمات. هذا **قرار مرحلي** وليس بديلًا دائمًا عن معمارية PostgreSQL/Redis المقترحة. المخطط الحالي يُهيَّأ عند تشغيل التطبيق؛ لا توجد سلسلة ترحيلات إنتاجية بعد، لذا لا تعدّل مخطط قاعدة مهمة دون نسخة احتياطية وخطة ترحيل.

## 3. ضمانات سير العمل الفعلية

- يجب أن يمر التشغيل بـ `awaiting_approval` ثم `awaiting_review`؛ لا يمكن لطلب `advance` تجاوز أي منهما.
- `version` يزداد في كل تغيير. كل طلب تعديل أو اعتماد أو إلغاء يحمل النسخة التي قرأها المستخدم، ويرفض الخادم الطلب القديم بـ `409`.
- تعديل المتطلبات متاح فقط قبل اعتمادها. حفظها يغير النسخة، فيبطل اعتمادًا أُرسل لنسخة أقدم.
- رقم `approved_version` يشير إلى حالة التشغيل المعتمدة، وليس معرف جدول تاريخ مستقل. النص السابق عند التعديل لا يُحتفظ به كاملًا في هذه النسخة؛ يسجّل الحدث فقط.
- فهرس SQLite فريد يمنع وجود تشغيلين غير منتهيين للمشروع نفسه.
- إنشاء تشغيل يستخدم `Idempotency-Key`، وإعادة إرسال المفتاح نفسه للمشروع تعيد التشغيل نفسه. لا يعتمد ذلك على حالة المتصفح.
- الطلبات المتزامنة تتسلسل بمعاملة كتابة؛ طلب انتقال واحد فقط يستطيع النجاح لنسخة معينة.
- الإلغاء نهائي. لا يُعاد فتح تشغيل مكتمل أو ملغى؛ يستطيع المستخدم إنشاء تشغيل جديد.
- التقدم مرتبط بصفحة المشروع، لا بمهام خلفية خفية. الإيقاف المؤقت لا يلغي طلبًا سبق وصوله للخادم؛ الإلغاء يكتب حالة نهائية عند نجاح المعاملة.
- عند العودة من صفحة أخرى أو إعادة تحميلها، تُقرأ البيانات من الخادم. الواجهة تعود للوحة الرئيسية بعد إعادة التحميل، ثم يمكن فتح المشروع واستئنافه.

## 4. الملفات وما تعنيه نتائج الفحص

الحزمة تحتوي أسماء ملفات ثابتة:

- `index.html`: قالب لوحة مهام جاهز، لا تُحقن فيه أسماء أو أوصاف أو تعليمات المستخدم.
- `requirements.md`: آخر نص متطلبات اعتمده المستخدم.
- `plan.md`: خطة تجهيز ثابتة توضح حدود المحاكاة.
- `README.md`: طريقة تشغيل الملف وحدود القالب.
- `report.json`: ثلاث نتائج لفحص وجود الملفات، مطابقة المتطلبات، ومطابقة القالب الموثوق.

التقرير يصرح بـ `code_executed: false` و`model_used: false`. نجاحه لا يعني أن Factory نفّذ التطبيق أو اختبر سلوكه أو حلل أمانه. اختبارات Playwright الموجودة في المستودع تختبر **القالب الثابت المعروف** وسلوك المصنع؛ ليست خدمة اختبار لأي كود يقدمه المستخدم.

لا يحوّل تعديل المتطلبات القالب إلى تطبيق مخصص. أي فكرة خارج إمكانات لوحة المهام تُحفَظ للتخطيط فقط في هذه النسخة، ويُذكر هذا القيد في نموذج الإنشاء وفي مساحة المشروع والوثائق.

## 5. حدود الأمان

### ما هو مطبق

- SQL parameterization للبيانات الواردة؛ لا يُركّب SQL من أسماء ملفات أو قيم مستخدم.
- تحقق Pydantic من الأطوال والقالب المسموح، ورفض الحقول الإضافية.
- لا مفاتيح API ولا استدعاءات نموذج ولا تنفيذ shell.
- لا أسماء ملفات يختارها المستخدم؛ قائمة مسموحة عند بناء ZIP.
- يعرض المصنع محتوى الملفات كنص في React، لا HTML قابل للتنفيذ.
- القالب يستخدم `textContent` لعرض المهام، لا `innerHTML`.
- المعاينة تستخدم `sandbox="allow-scripts allow-forms"` **دون** `allow-same-origin` أو صلاحيات نوافذ/تنزيلات/تنقل أعلى. السماح بالنماذج مطلوب حتى يصل حدث الإضافة إلى JavaScript؛ CSP تمنع إرسال النماذج فعليًا إلى وجهة خارجية.
- CSP داخل القالب تمنع الشبكة والموارد الخارجية (`default-src 'none'`, `connect-src 'none'`, `form-action 'none'`). السماح بالأنماط والسكريبت المضمنين خاص بالقالب الثابت فقط.
- لا توجد مشاركة localStorage أو ملفات جلسة مع أصل المصنع داخل الإطار. الحفظ المحلي قد لا يتاح في المعاينة؛ تظهر رسالة بديلة.
- API ترفض عمليات تعديل ذات `Sec-Fetch-Site: cross-site`، وتطلب JSON للعمليات ذات الجسم، ولا تفعّل CORS عامًا. هذه حماية إضافية لا تعوض المصادقة أو التفويض.
- الموارد تعرض `no-store` للـ API و`nosniff`. لا يُستخدم `NEXT_PUBLIC_` لعنوان API الخلفي.
- الواجهة توضّح أن المساحة بلا مصادقة وتطلب بيانات تجريبية فقط.

### ما ليس مطبقًا

- لا عزل بين المستخدمين، ولا هوية صاحب الموافقة. كل من يصل إلى هذه النسخة يشارك نفس المساحة ويمكنه تعديلها وحذف مشاريعها.
- لا تشفير تطبيقي لقاعدة البيانات، ولا تدقيق أمني خارجي، ولا rate limiting إنتاجي.
- لا عزل OS لتشغيل كود غير موثوق لأن هذا النوع من التنفيذ غير متاح أصلًا.
- iframe الحالي ليس ترخيصًا لاستضافة كود مولّد بحرية. قبل ذلك يجب تنفيذ Runner/بوابة منفصلة، سياسات شبكة وموارد، ونموذج تهديد واختبارات مناسبة.

**قرار الإتاحة:** مناسبة للتطوير والتجربة ببيانات وهمية. غير مناسبة لخدمة عامة أو لبيانات خاصة.

## 6. الاختبارات والأتمتة

- اختبارات pytest بقواعد مؤقتة مستقلة تشمل الحالات، الموافقات، التعديل، التزامن، الإلغاء، idempotency، بقاء البيانات، حذف العلاقات، التصدير والتحقق من المدخلات.
- اختبارات Playwright للمسار من الإنشاء حتى ZIP، إضافة المهام وإنجازها وحذفها في iframe، منع وصوله إلى الأصل المضيف والشبكة، عرض مدخلات HTML كنص، استعادة البيانات بعد إعادة التحميل، الهاتف، القوالب، البحث وتأكيد الحذف، استقلال المحاولات الملغاة، التنقل بلوحة المفاتيح، والتعافي من فشل الاتصال.
- TypeScript checking وبناء Next.js للإنتاج، وتنسيق Prettier، وفحص Python وتنسيقه باستخدام Ruff.
- GitHub Actions مهيأ لتشغيل الفحوص؛ يحتاج push/PR ليُنفّذ على GitHub. لم يُنشأ نشر إنتاجي.
- مساعد Chromium المعبأ عبر npm اختياري لبيئات Linux المقيدة. لا يعطل Web Security أو عزل الأصول في المتصفح الاختباري. استخدام `--no-sandbox` في حاوية الاختبار ليس Runner آمنًا ولا جزءًا من التطبيق.

## 7. ترتيب العمل التالي

1. اعتماد مزود المصادقة وتطبيق الجلسات والملكية واختبارات الوصول بين المستخدمين.
2. ترحيل SQLite إلى PostgreSQL بمخطط نسخ متطلبات واعتمادات مستقل، مع حفظ بيانات التجارب المهمة إن لزم.
3. نقل الانتقالات إلى عامل مهام قابل للاستعادة، وإضافة outbox وSSE.
4. ربط مزود نموذج واحد لتحليل المتطلبات أولًا، بعقود مخرجات وحدود رموز وتكلفة، ورفض توسع النطاق الصامت.
5. تنفيذ Runner وسياسة التبعيات والعزل قبل توليد وتشغيل مشاريع مخصصة.

تبقى مراجعة المتطلبات واعتماد التسليم إلزاميين خلال التوسعة، ولا يُضاف نشر تلقائي إلى الإنتاج ضمنيًا.
